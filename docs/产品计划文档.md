## 0. 阅读指引与术语

**术语表（Glossary）**

| 术语 | 定义 |
| --- | --- |
| 开发板定义（BoardDefinition） | 一块真实开发板的声明式描述，含引脚清单与引脚能力，如 `esp32-devkitc-v4` |
| 组件定义（ComponentDefinition） | 一类元器件的声明式描述，含端口、属性、图标，如 `dht11`、`sg90` |
| 组件实例（ComponentInstance） | 画布上的一个具体器件，引用某个组件定义并持有位置、端口配置 |
| 端口（Port） | 组件实例上可连线的端点（如 DHT11 的 `VCC` / `DATA` / `GND`） |
| 引脚（Pin） | 开发板上的物理引脚（如 ESP32 的 `GPIO4`），是端口连接的另一端 |
| 连线（Connection） | 一条端口→端口或端口→引脚的连接记录 |
| 网络（Net） | 一组电气等价的连线集合（如所有 GND 归同一个 net），面包板场景必需 |
| 校验规则（Rule） | 一条可独立启停的检查逻辑，输入画布快照，输出诊断项 |
| 诊断项（Diagnostic） | 一条校验结论（severity + 规则码 + 消息 + 关联对象） |
| 定义版本（definitionVersion） | 组件/开发板定义的语义化版本号，用于保证历史项目可复现 |

## 1. 项目启动信息（总控模板必填项）

- **项目名称**：2D 可视化单片机接线仿真与测试平台（Web 端）
- **初始需求**：在 2D 画布中摆放主控芯片与常见外设，连线后校验"连线是否连通、端口选择是否正确、主控引脚定义是否与真实硬件一致"；含前端布局、组件库、控制面板、运行校验四块。
- **项目类型**：前后端分离 Web 应用（前端图形编辑器 + 后端规则与数据服务）
- **业务目标**：让学生在没有实物器材时也能验证接线方案，降低"接错线烧板子"的试错成本；让教师/作者可复用同一套引脚与规则数据。
- **成功标准**：
  1. 用户能在 5 分钟内完成"放 ESP32 + DHT11 + OLED + 连线 + 运行"，并获得可信的校验结论；
  2. ESP32 引脚定义与官方技术资料逐项一致（详见第 8 章与 AC-01）；
  3. 新增一款芯片或一个组件时，**只改数据、不改核心代码**（新增开发板 ≤ 1 个声明文件；新增组件 ≤ 1 个声明文件 + 可选 1 条规则）。
- **技术栈（推荐）**：React + TypeScript + Vite + React Flow（画布）+ Zustand/TanStack Query + NestJS + Prisma + PostgreSQL（本地开发 SQLite）
- **是否存在终极功能**：是
- **终极功能定义**：用户完成连线并点击"运行"后，平台输出一份**可定位、可解释、与真实硬件引脚定义一致**的校验报告，且报告可通过新增规则与新增组件定义持续扩展，无需改动核心引擎。
- **技术约束**：
  - 性能：30 组件 / 50 连线规模下交互帧率 ≥ 50 FPS；校验接口 P95 < 300 ms
  - 兼容性：Chrome / Edge 最新两个大版本（Firefox 与 Safari 尽力支持，不作为门禁）
  - 安全：无用户上传可执行内容；无凭证入库；接口不做越权写入
  - 可维护性：组件与规则均声明式注册，禁止在核心引擎内写 `if (componentType === 'DHT11')` 这类分支
- **默认循环轮次**：3 · **安全最大轮次**：6 · **每轮最大改动点数**：3
- **角色配置**：主控（总控与验收）+ 架构师 + 程序员 + 测试员

## 2. 背景与目标

### 2.1 背景

单片机入门教学与自学场景中，学生常在"接线"环节出错：引脚认错（把仅输入引脚当输出用）、电平不匹配（5V 器件直连 3V3 GPIO）、必要引脚缺失（I2C 没有上拉电阻）、协议引脚接反（TX 接 TX）。这些错误的反馈成本很高——可能烧毁器件或开发板。

现有替代方案的不足：

| 现状 | 问题 |
| --- | --- |
| 看图纸/教程照抄 | 无法在动手前验证自己的改法是否正确 |
| 真实面包板试错 | 成本高、损坏风险、无法回滚 |
| 专业 EDA（Proteus 等） | 学习门槛高、体积大、需安装，不适合轻量教学 |
| 通用白板工具 | 只画线不校验，没有引脚定义库 |

### 2.2 目标（本期）

1. **可视化接线**：拖拽摆放组件、端口间连线，替代纸面连线图。
2. **可校验**：点击运行给出连通性、端口合法性、引脚冲突、必要连接缺失四类结论。
3. **引脚真实**：主控引脚编号、名称、能力分类与真实开发板一致。
4. **可扩展**：新增芯片/组件/端口/规则走声明式注册，核心引擎不变。

### 2.3 非目标（明确不做）

| 非目标 | 说明 |
| --- | --- |
| 固件烧录与下载 | 不做串口/编译/烧录链路 |
| CPU 指令级仿真 | 不模拟程序执行、不做时序/中断模拟 |
| 电气级精确仿真 | 不做电流求解、不做精确电压降，仅做"域级/能力级"约束检查 |
| 3D 视图 | 仅 2D |
| 协同实时编辑 | MVP 不做多人同编（架构预留，见第 12 章 E-10） |
| 真实原理图/PCB 生成 | 不产出网表文件（后续可考虑导出，列 P3） |

### 2.4 In Scope / Out of Scope（本期）

| In Scope | Out of Scope |
| --- | --- |
| ESP32 开发板引脚模型（真实完整） | STM32 具体板型引脚（本期仅留扩展位） |
| 约 20 类基础组件的定义与端口 | 全部电商元器件库 |
| 画布拖拽/连线/缩放平移/网格对齐 | 自由曲线绘制、图形美化编辑 |
| 20 条内置校验规则 | 用户自定义规则编辑器 |
| 项目保存 / 导出导入 JSON | 账号体系与团队协作（MVP 待定，见第 3 章 A-05） |
| 校验结果列表与画布定位 | 自动修复（autoFix 仅预留字段） |

## 3. 假设与待确认决策

> 产品方已授权"不确定处先列假设后继续"。以下每条均给出**候选方案 + trade-off + 推荐项 + 假设标注**，不阻塞开发；若与产品预期不符，请在评审时纠正，纠正成本从低到高排列。

### A-01 画布技术方案（影响面：大）

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **React Flow（@xyflow/react）** | 节点/端口/连线是原生概念；`Handle` 即端口；内置缩放平移、选中、Minimap、自定义节点、边类型 | 只擅长"节点-连线"范式，面包板内部节点需自行建模 | **推荐** |
| Konva | 2D 绘制能力最强，自由度最高 | 连线命中、端点吸附、缩放坐标系、选中框全部要自研，MVP 工期翻倍 | 备选（后续若要做面包板内部插孔级仿真再评估） |
| Fabric.js | 上手快，图形编辑友好 | 连线语义（端口/多段线/箭头/删除）需大量自研；对"图"结构支持弱 | 不选 |
| 纯 SVG 自研 | 无依赖、可控 | 等于重写一遍 React Flow 的成熟能力 | 不选 |

**假设标注**：默认采用 React Flow。若产品要求"面包板插孔级高保真还原"，则需在 M3 之后评估 Konva。

### A-02 后端语言（影响面：大）

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **Node.js + NestJS + TypeScript** | 与前端同语言，`packages/contracts` 共享类型（请求/响应/枚举单一真相源）；Nest 的 Module + Provider 天然承载"规则/组件注册表"的插件式机制 | 计算密集场景性能弱于 Go/Rust（本期无此需求） | **推荐** |
| Python + FastAPI | 后续若接 LLM 辅助诊断、SPICE 类计算，生态更好；开发快 | 类型无法与前端直接共享，需靠 OpenAPI 生成，契约漂移风险更高 | 备选（若未来引入电气计算/模型推理，可独立成服务） |
| Go + Gin | 性能与部署简单 | 开发效率与生态对"声明式规则 + JSON 数据"场景收益不明显 | 不选 |

**假设标注**：默认 NestJS。若团队已有 Python 主力，则改 FastAPI，此时契约以 `openapi.yaml` 为唯一真相源。

### A-03 数据库（影响面：中）

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **PostgreSQL** | JSONB 存引脚/规则参数（半结构化）；支持后续多用户、全文检索、并发写；生产标准 | 本地需 Docker 或安装服务 | **生产推荐** |
| SQLite | 零依赖，单机 MVP 最快落地 | 无 JSONB 索引能力（JSON1 有限）、并发写弱、不适合多用户 | **MVP 本地开发推荐** |

**推荐做法**：Prisma + PostgreSQL 为生产目标；MVP 与本地开发用 SQLite（同一套 Prisma schema，`provider` 通过环境变量切换），并在 `packages/contracts` 中用 Zod 做写入校验，避免依赖 DB 特有的 JSONB 校验能力。
**接受的代价**：SQLite 与 PostgreSQL 在枚举、数组类型、大小写敏感性上存在差异，CI 必须跑一次 PostgreSQL 集成测试（见 AC 与第 15 章）。

### A-04 接口风格（影响面：中）

| 方案 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **REST + OpenAPI 3.1** | 与"资源型数据（项目/定义/校验结果）"匹配；易缓存、易调试、易生成 SDK | 复杂聚合查询需多次请求 | **推荐** |
| GraphQL | 前端可按需取字段 | 引入复杂度高；本项目查询形态固定，收益低 | 不选 |
| tRPC | 端到端类型安全最好 | 强绑定 TS 全栈，不利于将来对外开放 API | 不选（仅内部可考虑） |

**补充**：MVP 不引入 WebSocket；预留 `/api/v1/ws` 命名空间用于后续协作与长任务进度（见第 12 章扩展点 E-05）。

### A-05 项目归属与保存策略（影响面：中，需产品确认）

**假设**：**MVP 不做账号体系**，采用"浏览器本地匿名项目 ID（UUID）+ 服务端匿名项目存储（30 天 TTL）+ 手动导出/导入 JSON"。理由是账号体系会显著拉长 MVP 周期，而本期核心价值在"校验能力"而非"云协作"。

- 若产品要求 MVP 即支持登录与跨设备同步，则新增约 1 个 Wave（认证 + 权限 + 项目归属），里程碑顺延，M4 可延后。
- 撤销条件：出现"同一用户多设备使用"的真实诉求，或需要教师统一管理学生作业。

### A-06 主控型号基准（影响面：中）

**假设**：ESP32 以 **ESP32-DevKitC V4（ESP32-WROOM-32 模组）** 为基准板型。若实际教学使用 ESP32-S3/ESP32-C3 或 ESP32-DevKitC-32E，引脚能力表需替换（数据结构不变，仅换定义文件）。

### A-07 校验执行位置（影响面：中）

**假设**：**前端本地规则引擎 + 后端权威校验双轨**。前端内置一套默认规则集，保证离线也能给出基础结论（体验）；点击运行时同时请求后端 `POST /api/v1/validate`，以后端返回的规则集版本与结论为准，并提示两者差异（防止规则过期）。
Trade-off：存在两套实现的一致性成本，故要求规则逻辑写在共享包 `packages/rule-engine`（纯函数、无运行时依赖），前后端复用同一份实现，仅数据源不同。

### A-08 面包板语义粒度（影响面：中）

**假设**：MVP 把面包板建模为**"带内部导通分组的端口集合"**（电源轨 2 组 + 中间 30 列 × 2 组，每组内插孔等价），不建模插孔级物理坐标与跨槽干涉。理由：插孔级建模与 UI 复合度会挤占本期核心（引脚真实性 + 规则引擎）预算。

### A-09 引脚数据来源与校核方式（影响面：中）

**假设**：引脚定义由**官方技术参考手册/数据手册人工录入 + 录入后在平台上做"自查页"交叉核验**（见 H-3 校验自查页），不依赖第三方库。录入成果必须可追溯到来源 URL 与版本号，作为 `sourceRef` 字段落库。

## 4. 用户场景与核心流程

### 4.1 用户角色

| 角色 | 诉求 | 关键指标 |
| --- | --- | --- |
| 学生/自学者（主用户） | 动手前验证自己的接线方案对不对 | 从打开到得到结论 ≤ 5 分钟 |
| 教师/助教 | 发布标准接线方案、检查学生答案 | 可导出/导入项目 JSON，结论可解释 |
| 内容作者/维护者 | 新增芯片与组件、维护引脚定义 | 新增组件不写核心代码 |
| 平台开发者 | 扩展规则、接入新板型 | 规则可独立启停、可单测 |

### 4.2 核心流程（主路径）

```
① 打开平台 → 新建项目（自动选择默认开发板 ESP32-DevKitC V4）
        ↓
② 左侧组件库按分类浏览/搜索 → 拖拽组件到画布（如 DHT11）
        ↓
③ 芯片与组件自动排布/手动移动；网格吸附对齐
        ↓
④ 从端口拖出连线到目标端口/引脚（类型不兼容时给即时提示）
        ↓
⑤ 左侧菜单下方出现控制面板：为每个组件选择端口用途、启用/禁用连接
        ↓
⑥ 点击右上角「运行」→ 本地规则引擎即时出结果 → 后端权威校验回填
        ↓
⑦ 结果面板列出：错误 / 警告 / 通过项；点击任一条 → 画布高亮定位
        ↓
⑧ 修正连线 → 再次运行 → 全部通过 → 保存项目 / 导出 JSON
```

### 4.3 异常与边界流程

| 场景 | 期望行为 |
| --- | --- |
| 画布为空点击运行 | 提示"画布中还没有组件"，不请求后端，不报错 |
| 只有组件没有连线 | 允许运行，输出"必要连接缺失"类诊断（提示性） |
| 拖拽形成自环（端口连自身） | 禁止创建，给出即时 Toaster 提示 |
| 同一端口重复连线 | 允许（形成 net），但触发端口占用/多驱动检查 |
| 后端不可用 | 降级为本地规则集结果，结果面板顶部标注"离线模式（规则集 vN，可能过期）" |
| 校验请求超时（> 3 s） | 取消请求，保留本地结果 + 提供"重试"按钮 |
| 误删组件 | 支持撤销（Ctrl/Cmd+Z），MVP 至少保留 20 步 |

## 5. MVP 范围与优先级

### 5.1 优先级定义

- **P0**：本期必须交付，缺失则 MVP 不成立
- **P1**：本期尽量交付，可顺延一个 Wave
- **P2**：明确排到后续迭代（第 12 章）

### 5.2 功能清单与需求编号

| 编号 | 功能 | 优先级 | 验收要点 |
| --- | --- | --- | --- |
| FR-01 | 三栏布局（左组件库+控制面板 / 右画布 / 右上运行按钮） | P0 | 布局在 1440×900 与 1920×1080 下不出现横向滚动条 |
| FR-02 | 组件库分类展示 + 搜索 | P0 | 6 个分类全部可见；关键词搜索 ≤ 300 ms 出结果 |
| FR-03 | 拖拽组件到画布（拖拽放置） | P0 | 从菜单拖入落点误差 ≤ 1 格 |
| FR-04 | 组件移动 / 删除 / 多选 | P0 | 支持框选；Delete 键删除；撤销可恢复 |
| FR-05 | 端口→端口连线（创建/删除/选中查看） | P0 | 连线两端必须是端口；不允许自环 |
| FR-06 | 缩放（滚轮/按钮）与平移（空格拖拽/中键） | P0 | 缩放范围 0.25x–2x；平移后视图坐标正确 |
| FR-07 | 网格与吸附对齐 | P1 | 开关可切换；吸附阈值 8 px |
| FR-08 | 控制面板：端口用途选择、连接启用/禁用 | P0 | 交互变更即时反映到连线样式与校验输入 |
| FR-09 | 运行按钮 → 触发校验 | P0 | 3 s 内出结果（本地即时 + 后端回填） |
| FR-10 | 校验结果面板（错误/警告/通过 + 定位） | P0 | 点击诊断项定位并高亮目标，误差为 0（见 AC-06） |
| FR-11 | ESP32 真实引脚模型 | P0 | 与官方资料逐项核验通过（AC-01） |
| FR-12 | 校验规则集（20 条） | P0 | 每条有单测；规则可独立启停 |
| FR-13 | 项目保存 / 打开 / 导出导入 JSON | P0 | 往返一致性（AC-07） |
| FR-14 | 离线降级（后端不可用） | P1 | 明确标注离线模式与规则集版本 |
| FR-15 | 撤销/重做 | P1 | ≥ 20 步 |
| FR-16 | 示例项目模板（1 键载入"ESP32 + DHT11 + OLED"） | P1 | 载入后可直接运行并全绿 |

### 5.3 MVP 范围一句话边界

> 交付"能放、能连、能自检、能保存"的 ESP32 接线校验器；不交付账号体系、不交付 STM32、不交付固件相关能力。

### 5.4 非功能需求

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 性能（前端） | 30 组件 / 50 连线：拖拽与连线时 ≥ 50 FPS；首屏可交互 < 2 s |
| NFR-02 | 性能（后端） | `POST /validate`（100 组件 / 150 连线）P95 < 300 ms |
| NFR-03 | 可用性 | 核心流程（放组件→连线→运行→看结果）无需文档引导即可完成 |
| NFR-04 | 可访问性 | 关键操作有键盘替代（Delete 删除、Esc 取消、Ctrl+Z 撤销）；焦点可见 |
| NFR-05 | 兼容性 | Chrome/Edge 最新两版为门禁；Firefox 尽力 |
| NFR-06 | 可维护性 | 新增组件/板/规则不改引擎（见第 12 章） |
| NFR-07 | 可观测性 | 后端请求日志含 requestId、规则集版本、耗时、诊断数量 |

### 7.3 组件定义的声明式内容（每个组件一份）

```
ComponentDefinition
├── identity: slug, displayName, aliases[], category, iconKey, tags[]
├── version: semver
├── ports[]: { id, name, role(signal|power|ground|passive), direction(in|out|io|na), 
│              electrical: { voltageDomain, currentLimitHint }, 
│              defaultConnection: 'required'|'optional'|'forbidden' }
├── interface: { protocols: [I2C|SPI|UART|OneWire|PWM|GPIO|Analog], busGroups[] }
├── portOptions[]: 运行时可选配置（如 I2C 地址、阻值、是否内部上拉）
├── requirements[]: 声明式依赖（如 "需要 10k 上拉到同电压域"、"信号线需要串联电阻"）
├── attrs[]: 展示用属性（尺寸、供电范围、引脚间距）
├── sourceRef: { docUrl, revision }   ← 数据可追溯
└── renderHints: { nodeWidth, nodeHeight, portLayout: 'left-right'|'top-bottom'|'grid' }
```

> **关键设计**：`requirements[]` 是"组件自我声明的约束"，由通用规则读取（如 R-12 上拉、R-19 限流电阻），**避免为每个组件写专属规则**，这是扩展性的核心机制。

## 8. 引脚模型与真实性要求

### 8.1 引脚数据模型

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 稳定唯一键，格式 `pin-<boardSlug>-<physicalLabel>`，如 `pin-esp32-devkitc-v4-gpio4` |
| `physicalLabel` | string | 板子丝印，如 `GPIO4`、`D4`、`3V3`、`GND` |
| `number` | int | 排针物理序号（1 起） |
| `aliases` | string[] | 常见别名：`IO4`、`D4`、`TOUCH0`、`ADC2_CH0` |
| `kind` | enum | `io` / `power` / `ground` / `enable` / `nc` |
| `capabilities` | enum[] | `GPIO` `INPUT` `OUTPUT` `ADC1` `ADC2` `ADC_CHn` `DAC` `PWM` `TOUCH` `I2C` `SPI` `UART` `STRAP` `XTAL` |
| `voltageDomain` | enum | `3V3` / `5V` / `VIN` / `GND` |
| `maxCurrentMa` | number? | 建议驱动上限（用于 R-15 提示） |
| `constraints` | object | 结构化限制：`{ inputOnly, internalPull: 'up'|'down'|'both'|'none', bootStrapping, flashReserved, adc2WifiConflict, notes }` |
| `side` / `order` | left/right + int | 渲染排布，与真实板子一致 |
| `sourceRef` | object | `{ docUrl, revision }` 数据来源 |

### 8.3 引脚真实性保障机制

| 机制 | 做法 |
| --- | --- |
| 数据可追溯 | 每个板定义含 `sourceRef`（官方文档 URL + 版本/日期） |
| 交叉核验 | 提供内部"引脚自查页"（dev-only 路由 `/dev/pin-audit`），以表格列全部引脚与能力，支持导出 CSV 供人工与 datasheet 逐行核对 |
| 结构校验 | 板定义提交时运行 `validate-board` 脚本：检查引脚 id 唯一、number 连续无缺、能力枚举合法、电压域必填、仅输入引脚不得声明 PWM |
| 一致性测试 | 单测断言关键事实（如 34–39 不含 OUTPUT、6–11 标记不可用、ADC1 为 32/33/34/35/36/39），数据改动若破坏这些断言则 CI 失败 |
| 变更留痕 | 引脚定义每次修改必须附来源链接与变更原因（PR 模板强制） |

## 9. 连线与校验规则

### 9.1 连线模型与建立规则

| 规则 | 说明 |
| --- | --- |
| 端点约束 | 连线两端必须是"端口"（组件端口或开发板引脚），不允许连到画布空白或节点主体 |
| 自环禁止 | 不允许同端口自连 |
| 重复连线 | 允许（归入同一 net），但触发 R-03/R-04 类检查 |
| 方向自由 | 物理上证允许 A→B 与 B→A；协议层交叉要求由规则检查（R-20） |
| 类型判定 | 创建时做**即时软校验**（不阻断）：若两端 role 明显冲突（如 ground ↔ signal），显示黄色警告但仍允许连（教学需要"故意连错"的场景） |
| 悬空端 | 拖拽中松手在非法区域 → 取消连线创建，不产生残留 |
| 连线禁用 | 控制面板可禁用连线，禁用者不参与校验（灰化显示） |

### 9.2 net 归并规则

1. 所有 `GND` 类端口/引脚归并为 **单一地网络**（后续可扩展为多电源域）。
2. 同一 `Power` 端口直连归为对应电压域网络（`3V3` net 与 `5V` net 分离，跨域直连触发 R-05）。
3. 面包板：同组插孔归并为一个内部 net（见 A-08）。
4. 信号线默认一条连线一个 net；同一信号点连接多器件时（如 I2C 总线）通过"多端点 net"表达。

### 9.3 校验规则清单（MVP 20 条）

> 规则以**纯函数 + 声明式元数据**实现：`input: ProjectSnapshot, context: RuleContext → Diagnostic[]`。全部规则可从规则集启停，severity 可配置。

| 规则码 | 名称 | 严重度 | 触发条件 | 建议信息 |
| --- | --- | --- | --- | --- |
| R-01 | 必要端口未连接 | error | 组件端口 `defaultConnection='required'` 且未连线 | 提示缺失端口名 |
| R-02 | 悬空电源/地 | error | 电源或 GND 端口已连但 net 中无有效来源（无板载供电或电源模块） | 提示接入 3V3/5V/GND |
| R-03 | 引脚重复占用（多驱动） | error | 同一 GPIO 被 ≥2 个输出型端口连接 | 列出所有占用方 |
| R-04 | 输出-输出冲突 | error | 同一 net 上 ≥2 个 `direction='out'` 端口 | 提示改为输入或分离 |
| R-05 | 电压域不匹配 | error | 5V 器件信号端口直连 3V3 GPIO（无电平转换模块） | 建议加电平转换/分压 |
| R-06 | 电源缺失 | error | 组件有 `power` 端口但 net 中无电源来源 | 提示接 VCC/VIN |
| R-07 | 未共地 | error | 组件有 `ground` 端口但未接入统一地网络 | 提示接入同一 GND |
| R-08 | 仅输入引脚被当输出 | error | `constraints.inputOnly=true` 的引脚承载了输出型 net 或 PWM 需求 | 提示换用可输出引脚 |
| R-09 | 仅输入引脚接上拉需求 | warning | 仅输入引脚被配置为需要内部上拉（其无内部上拉） | 建议外接上拉 |
| R-10 | Flash 保留引脚被占用 | error | 使用 GPIO6–11 | 明确提示不可用及原因 |
| R-11 | ADC2 与 WiFi 冲突 | warning | 板配置启用 WiFi 场景且 ADC2 引脚被用作模拟输入 | 建议改用 ADC1 引脚 |
| R-12 | 上拉电阻缺失 | warning | 组件 `requirements` 声明需要上拉，但 net 中无电阻到同电压域 | 建议 4.7k/10k 上拉 |
| R-13 | I2C 地址冲突 | error | 同一 I2C 总线上 ≥2 个从设备配置相同地址 | 列出冲突设备与地址 |
| R-14 | 协议引脚未成组/混总线 | error | 同组协议引脚（SCL/SDA、MOSI/MISO/CLK/CS）接在不同总线/不同引脚组 | 提示正确分组 |
| R-15 | 驱动能力超限 | warning | net 负载（如电机、舵机）直连 GPIO 且超 `maxCurrentMa` 提示值 | 建议用驱动/独立供电 |
| R-16 | 启动敏感引脚占用 | warning | 使用 strapping 引脚（0,2,5,12,15）接外设 | 说明上电电平影响 |
| R-17 | 串口引脚被占用 | warning | 使用 GPIO1/GPIO3 | 说明影响日志与下载 |
| R-18 | 电源短路 | error | 同一 net 内同时存在 3V3/5V 与 GND（非经元件） | 高优先级错误 |
| R-19 | 限流/保护元件缺失 | warning | LED 类组件未串联电阻；感性负载无续流（元数据声明） | 建议串联/并联保护 |
| R-20 | 串口 TX/RX 未交叉 | error | UART 类型两端同为 TX 或同为 RX | 提示 TX→RX 交叉连接 |

**规则元数据（每条规则必须提供）**：`code`、`name`、`severity`（默认值 + 可配置）、`scope`（`connection` / `component` / `board` / `project`）、`messageTemplate`、`suggestionTemplate`、`docAnchor`、`enabledByDefault`、`tags`（教学分类）。

### 9.4 校验执行流水线与结果语义

```
ProjectSnapshot
   ↓ [1] 结构校验（schema、id 唯一性、悬空引用）
   ↓ [2] net 归并（R-02/R-06/R-07/R-18 的前置）
   ↓ [3] 板级能力校验（R-08/R-10/R-11/R-16/R-17）
   ↓ [4] 电气域简化校验（R-05/R-15/R-19）
   ↓ [5] 协议校验（R-13/R-14/R-20）
   ↓ [6] 组件声明式需求校验（R-01/R-12）
   ↓ [7] 汇总 → 诊断列表（按 severity 排序，稳定排序键 = code + targetId）
```

| 结果状态 | 判定 | UI 表现 |
| --- | --- | --- |
| `passed` | 无 error 且无 warning | 绿色状态条 ✔ |
| `warning` | 有 warning、无 error（教学宽松模式） | 黄色状态条 ⚠ |
| `failed` | 存在 ≥1 error，或严格模式下 ≥1 warning | 红色状态条 ✖ |

### 10.3 反选论证（为何不选备选）

| 备选 | trade-off | 为何在本项目约束下不可接受 |
| --- | --- | --- |
| **Konva / Fabric.js** | 自由度高，但连线端点吸附、命中测试、坐标系变换、选中框、Minimap 均需自研 | 本项目核心差异化价值在"引脚真实性 + 规则引擎"，画布只是载体。自研图编辑内核会挤占 60%+ 工期，且长期维护成本高 |
| **Vue 3 + Vue Flow** | 同样成熟，但 React Flow 生态（自定义节点示例、Minimap、专业版能力路径、社区问答量）更大 | 团队若无强 Vue 约束，React 的成熟度更利于"长期维护"目标；若团队为 Vue 背景则此项反转，架构其余部分不受影响 |
| **Redux Toolkit** | 可预测、DevTools 强，但样板代码多、Provider 层级深 | 画布拖拽期间每秒数十次状态更新，RTK 的 action/selector 开销与样板会拖慢迭代 |
| **FastAPI** | 开发速度快、Python 生态利于后续电气计算/LLM | 无法与前端共享 TS 类型，契约一致性只能靠 OpenAPI 生成，规则引擎也无法前后端复用同一份实现（A-07 要求复用）→ 直接增加"两套规则实现漂移"风险 |
| **GraphQL** | 前端按需取字段 | 本项目查询形态固定（定义读取、项目 CRUD、校验），收益低而引入复杂度（schema 维护、N+1、缓存策略） |
| **MySQL** | 运维普及 | JSONB 的能力（半结构化引脚/规则参数检索、GIN 索引）弱于 PostgreSQL，而本项目定义数据大量为半结构化 |
| **纯前端 + localStorage（无后端）** | 架构最简、零成本部署 | 违背"必须前后端分离"的明确要求；规则集无法集中升级；项目无法跨设备；扩展开销在后期集中爆发 |

### 10.4 接受的代价（已知技术债）

1. **规则引擎双端复用带来包体积**：前端需内置规则引擎（约 20–40 KB gzip），需做代码分割，仅在校验模块加载。
2. **SQLite 与 PostgreSQL 行为差异**：CI 必须保留一条 PostgreSQL 集成测试；禁止使用 DB 特有 JSON 查询语法（统一用 Prisma + 应用层 Zod 校验）。
3. **React Flow 的边界**：面包板"插孔级"仿真超出其舒适区；若产品后续要求，需评估 Konva 迁移（迁移面被隔离在 `features/canvas`）。
4. **无账号体系（A-05）**：匿名项目依赖本地 UUID + TTL，清缓存会丢项目（用导出 JSON 缓解）。
5. **引脚数据人工维护**：新增板型成本随板型数量线性增长，靠"自查页 + 一致性单测"控制质量。

### 10.7 数据流

**链路 A：加载项目**

```
打开项目 → GET /api/v1/projects/:id
        → 响应含 project + 引用到的 boardDefinition / componentDefinitions（含版本）
        → 前端注入画布（React Flow nodes/edges）
        → 本地规则引擎预热（编译规则集）
```

**链路 B：运行校验**

```
点击「运行」
 → 前端：serialize(project) → ProjectSnapshot（规范化、稳定排序）
 → 本地引擎同步出结果（< 16 ms 目标）→ 结果面板立即渲染 + 顶部标"本地结果（规则集 vN）"
 → 并发 POST /api/v1/validate { snapshot, ruleSetVersion?, projectId? }
 → 后端：装配规则集 → 逐阶段执行 → 返回 { ruleSetVersion, status, diagnostics[], durationMs, projectRevision }
 → 前端：以后端结果覆盖渲染；若版本不一致，提示"规则集已更新至 vN+1"
 → 落库：validation_runs（可选，默认仅保存最近 20 次，见 11.2）
```

**链路 C：保存项目**

```
任意改动 → 本地 store 标记 dirty → 防抖 1.5 s 自动保存（PATCH /projects/:id）
        → 乐观更新 + 失败重试 2 次 → 顶部保存状态指示（已保存/保存中/失败）
        → 版本冲突（409）→ 提示"项目已在别处更新"，提供覆盖/另存为
```

### 10.8 模块边界审查

| 维度 | 检查结果 | 严重度 |
| --- | --- | --- |
| 依赖方向 | 单向无环（apps → packages，contracts 为叶子） | 通过 |
| 接口契约 | 前后端仅通过 `/api/v1` 与 `contracts` 通信；`rule-engine` 通过 `RuleContext` 接口注入数据 | 通过 |
| 数据持有 | `project` 归 `apps/api/modules/project` 唯一写入；`validation` 模块只读 project、只写 `validation_runs` | 通过 |
| 变更半径 | 新增组件 = 改 `definitions`（1 处）+ 前端图标映射（1 处新图标无需改动映射逻辑，用 `iconKey` 动态查表） | 通过 |
| 术语一致性 | `port` / `pin` / `connection` / `net` 在 contracts 中唯一定义，前后端禁止自定义同义别名 | 通过 |
| 待解决的边界风险 | **前端本地规则引擎**与**后端规则引擎**属同一逻辑两处运行 —— 若绕过共享包各自实现将产生漂移 | **警告**：必须强制从 `packages/rule-engine` 引入，ESLint 规则禁止在 `apps/web` 内重写规则逻辑 |

### 10.9 前端状态分层

| 状态类型 | 载体 | 生命周期 | 示例 |
| --- | --- | --- | --- |
| 画布状态 | Zustand + 时间旅行中间件（撤销栈） | 会话内 | nodes、edges、viewport、selection |
| 校验状态 | Zustand（本地结果） + TanStack Query（远端结果） | 会话内 | diagnostics、status、ruleSetVersion |
| 服务端状态 | TanStack Query 缓存 | 跨页面 | 组件定义、板定义、项目列表 |
| UI 临时状态 | 组件本地 state | 极短 | 面板折叠、拖拽中、hover |

**性能实现要点**：
1. React Flow 节点组件用 `memo` + 仅在自身数据变化时重渲染（避免拖拽时全量重绘）。
2. 连线期间使用"临时边"渲染，落点确定后才写入 store（避免每帧触发全局更新）。
3. 大项目（> 50 组件）启用 `onlyRenderVisibleElements`。
4. 规则引擎在 Web Worker 中执行（> 200 组件时），避免阻塞主线程（P1 优化项）。

### 10.10 后端关键实现要点

| 关注点 | 方案 |
| --- | --- |
| 错误处理 | 全局 `ExceptionFilter` 统一响应包络（见 11.5）；业务错误用领域异常类，禁止裸 `throw new Error` |
| 日志 | 结构化 JSON：`requestId`、`route`、`durationMs`、`ruleSetVersion`、`diagnosticCount`、`status` |
| 配置 | `@nestjs/config` + Zod 校验环境变量，缺失即启动失败（fail-fast） |
| 校验编排 | `ValidationService` 只做编排（装配规则集 → 调 engine → 存储），不内联规则逻辑 |
| 规则注册 | `RuleRegistry`：启动时扫描 `packages/rule-engine` 导出 + DB 中启停配置，生成 `RuleSet`（含版本号 = 规则码与参数的内容哈希） |
| 幂等 | 校验接口天然幂等（纯计算）；项目 PATCH 用 `If-Match: <revision>` 做乐观锁 |
| 可观测 | `/api/v1/health`、`/api/v1/version`（含规则集版本、定义版本） |

## 11. 数据模型与 API 草案

### 11.1 实体关系

```
User(可选, MVP 不启用)
  │
Project ──1:1──> BoardRef ──> BoardDefinition ──1:N──> PinDefinition
  │
  ├──1:N──> ComponentInstance ──N:1──> ComponentDefinition ──1:N──> PortDefinition
  │              │
  │              └──1:N──> PortConfig（端口运行时可选项）
  │
  ├──1:N──> Connection ──N:1──> Net（可选聚合）
  │
  └──1:N──> ValidationRun ──1:N──> Diagnostic

RuleSet ──1:N──> RuleConfig（启停 + severity 覆盖）
```

### 11.2 表结构草案（字段级）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `board_definitions` | `id`(slug+version) `slug` `displayName` `mcuFamily` `version`(semver) `revision` `sourceRef`(json) `pins`(json) `createdAt` | 引脚以 JSON 存储（半结构化，读取频繁但极少单独查询单引脚）；同时落 `pins` 的校验摘要字段用于列表页 |
| `component_definitions` | `id` `slug` `displayName` `aliases`(json) `category`(enum) `version` `ports`(json) `interface`(json) `portOptions`(json) `requirements`(json) `attrs`(json) `iconKey` `sourceRef` `enabled` | 定义数据可由 DB 装载，也可在启动时从 `packages/definitions` 同步（seed 幂等） |
| `projects` | `id`(uuid) `name` `description` `ownerKey`(匿名 UUID 或 userId) `boardRef`(slug+version) `schemaVersion` `revision`(int) `viewport`(json) `createdAt` `updatedAt` `expiresAt`(匿名 30 天) | `ownerKey` 为匿名标识，MVP 不做鉴权，但写入须带 ownerKey 防串数据（轻量隔离） |
| `component_instances` | `id`(uuid) `projectId` `definitionSlug` `definitionVersion` `label` `x` `y` `rotation` `enabled` `portConfig`(json) | 与项目分开存储便于增量 PATCH；也可整体存 JSON（见下方"存储策略"） |
| `connections` | `id`(uuid) `projectId` `fromType`(port/pin) `fromRef`(json) `toType` `toRef`(json) `kind`(signal/power/ground/bus) `enabled` `manualFlags`(json) | `fromRef` = `{ componentId, portId }` 或 `{ pinId }` |
| `nets` | `id`(uuid) `projectId` `kind` `memberRefs`(json) | 可由连线推导，落库用于缓存与快速诊断定位 |
| `rule_sets` | `id` `version`(内容哈希) `configSnapshot`(json) `createdAt` | 校验结果可复现的关键：记录本次使用的规则集版本 |
| `rule_configs` | `code` `enabled` `severityOverride` `params`(json) `updatedAt` | 后台可调，规则自身实现不变 |
| `validation_runs` | `id`(uuid) `projectId` `projectRevision` `ruleSetVersion` `status` `diagnostics`(json) `durationMs` `createdAt` | 默认只保留最近 20 条/项目（清理任务） |
| `diagnostics` | 内嵌于 `validation_runs.diagnostics`（json） | 单条诊断不需要独立表；若需统计报表再拆表 |

**存储策略说明**：`component_instances` 与 `connections` 既可规范化建表，也可作为 `projects.content`(json) 整体存储。**推荐规范化**，理由：便于后续做"组件使用统计""规则命中率统计""跨项目模板"等分析，且增量 PATCH 更快。代价是写入需事务包裹（一个项目一次保存 = 1 事务）。

### 11.3 版本化与可复现策略

| 对象 | 版本机制 | 目标 |
| --- | --- | --- |
| API | URL 前缀 `/api/v1`；破坏性变更开 `/api/v2`，v1 至少保留 2 个大版本周期 | 前端可独立发布 |
| 组件/板定义 | `version`(semver) + `revision`(内容哈希)；项目保存时**记录所用版本** | 历史项目重新打开结果不变；新增引脚不影响老项目 |
| 规则集 | `version` = 规则码+参数+severity 的内容哈希 | 校验结果可复现、可比对（AC：同快照 + 同规则集 → 诊断集合完全一致） |
| 项目 | `schemaVersion`（数据格式版本）+ `revision`（乐观锁） | 老格式可迁移；并发编辑可检测 |
| 迁移 | `packages/contracts/migrations/*`：`schemaVersion` 升版时提供迁移函数（纯函数，可单测） | 打开老项目自动迁移，不弹窗报错 |

### 11.5 统一响应包络与错误码

**成功包络**：`{ "data": <payload>, "meta": { "requestId", "ruleSetVersion?" } }`
**失败包络**：`{ "error": { "code", "message", "details"?, "requestId" } }`

| 错误码 | HTTP | 场景 | 前端处理 |
| --- | --- | --- | --- |
| `VALIDATION_FAILED` | 422 | 请求体不符合 schema | 高亮非法字段并提示 |
| `PROJECT_NOT_FOUND` | 404 | 项目 id 不存在或已过期 | 提示"项目已过期，请重新导入 JSON" |
| `PROJECT_REVISION_CONFLICT` | 409 | `If-Match` 与当前 revision 不一致 | 弹"覆盖 / 另存为" |
| `DEFINITION_NOT_FOUND` | 404 | 引用了未知组件/板 slug 或版本 | 提示缺失定义 + slug，允许"以占位节点打开"（不阻塞） |
| `SCHEMA_MIGRATION_FAILED` | 400 | 导入 JSON 迁移失败 | 展示失败原因与目标 schemaVersion |
| `PAYLOAD_TOO_LARGE` | 413 | 导入/保存超出大小限制 | 提示上限（2 MB） |
| `RULE_SET_VERSION_UNAVAILABLE` | 409 | 请求了不存在的规则集版本 | 降级为最新版本并提示 |
| `INTERNAL_ERROR` | 500 | 未预期异常 | 展示 requestId 供排查 |

### 11.6 分页、幂等、并发

| 关注点 | 方案 |
| --- | --- |
| 分页 | 组件列表用游标分页（`cursor` + `limit`，默认 20，上限 100）；校验历史用 `limit` + `beforeRunId` |
| 幂等 | `POST /validate` 天然幂等（纯函数 + 相同输入 → 相同输出）；`POST /projects` 支持 `Idempotency-Key` 头防重复创建 |
| 并发 | 项目 PATCH 用 `If-Match: revision` 乐观锁；冲突返回 409，不做静默覆盖 |
| 超时 | 前端 `POST /validate` 超时 3 s 取消并降级为本地结果 |
| 限流 | 单 IP 60 req/min（`/validate` 单独 30 req/min），超限 429 |

### 11.7 WebSocket 预留（不在 MVP）

命名空间 `/api/v1/ws`，事件草案：`project.updated`（协作）、`validation.progress`（大项目分片校验进度）、`ruleSet.updated`（规则热更新通知）。MVP 仅保留路径与网关骨架，不实现业务事件。

### 12.2 三条扩展标准作业路径（必须验证）

**E-01 新增芯片（如 STM32F103C8T6 BluePill）**

```
① 新建 definitions/boards/stm32f103c8t6-bluepill.ts（引脚表 + sourceRef）
② 本地跑 validate-board 脚本（id 唯一 / number 连续 / 能力合法）
③ 跑一致性单测（引脚数量、关键能力断言）
④ seed 同步到 DB（幂等；slug+version 唯一）
⑤ 前端无需改动：板选择器按 GET /boards 渲染，画布按 pins 渲染两列引脚
⑥ 验收：能在 UI 中选择该板、渲染全部引脚、连线并运行校验
```

**E-02 新增组件（如 DHT22）**

```
① 复制 components/dht11.ts 为 dht22.ts，改 slug/端口/属性/requirements
② 添加图标（iconKey 查表，无需改代码逻辑）
③ seed 同步 + 版本号 = 1.0.0
④ 前端组件库自动出现（按 category 分组）
⑤ 验收：拖入画布、连线、触发 R-01/R-12 等既有规则；无新增核心代码
```

**E-03 新增规则（如 R-21"PWM 引脚不支持"）**

```
① 新建 rules/pwm-capability.ts，导出 { meta: { code:'R-21', severity, scope, ... }, run }
② 单测：正例 + 反例 + 边界（无相关组件时返回 []）
③ 注册表自动收集 → 规则集版本哈希变化（前端收到提示）
④ 验收：既有项目运行后可按需出现 R-21 诊断；可被 rule_configs 关闭
```

**扩展性验收（AC-10）**：以上三条路径在 M4 前各实操一次并留证（提交记录 + 测试输出），且全程**未修改** `apps/api/modules/validation`、`apps/web/features/canvas` 的核心文件。

## 14. 行为契约（场景 / 输入 / 输出 / 异常 / 验收）

| 场景 | 输入 | 输出 | 异常/错误 | 验收标准 |
| --- | --- | --- | --- | --- |
| 打开平台 | 浏览器访问 | 三栏布局 + 默认板 ESP32 + 空画布 + 组件库 | 后端不可用 → 仍渲染 UI，顶部标注"离线模式"，定义使用内置快照 | 首屏可交互 < 2 s |
| 拖入组件 | 组件 slug + 画布坐标 | 画布出现组件节点，含端口 Handle | 未知 slug → Toaster 报错，不落节点 | 落点吸附误差 ≤ 1 格；同类型自动编号 |
| 创建连线 | 源端口 ref + 目标端口 ref | 连线创建并归并 net | 目标非法/自环 → 取消创建并提示原因 | 禁止非法连线产生残留 |
| 创建"可疑"连线 | ground ↔ signal | 创建成功但标黄 + 即时提示 | — | 允许教学场景故意错连 |
| 禁用连线 | connectionId + enabled=false | 连线灰化，校验输入中 `enabled=false` | 连线不存在 → 404 | 重跑后该连线相关诊断消失 |
| 运行校验 | ProjectSnapshot | `{ status, diagnostics[], ruleSetVersion }` | 超时 3 s → 取消 + 保留本地结果 + 重试按钮；后端不可用 → 离线结果 + 版本标注 | 有 error 时状态 `failed`；诊断可定位 |
| 点击诊断项 | diagnosticId | 画布视口移动到目标并高亮组件/端口/连线 | 目标已被删除 → 提示"目标已不存在"并禁用点击 | 定位后目标在视口内且高亮可见 |
| 保存项目 | 画布状态 | 顶部状态"已保存"，服务端 revision +1 | 409 冲突 → 覆盖/另存为；网络失败 → 重试 2 次后提示 | 刷新后画布与保存前一致 |
| 导出项目 | projectId | JSON 文件（含 schemaVersion + 定义版本） | 项目不存在 → 404 | 导出文件可被导入还原 |
| 导入项目 | JSON payload ≤ 2 MB | 新项目 id | 迁移失败 → 400 + 原因；超限 → 413 | 往返一致（AC-07） |
| 切换开发板 | boardSlug | 画布重载引脚；已有连线若引用旧引脚 → 标记失效并列入诊断 | 板定义缺失 → 提示并保持原板 | 切换后不出现崩溃或静默丢失连线 |
| 校验离线降级 | 断网 + 运行 | 本地结果 + "离线模式（规则集 vN）"标注 | — | 标注可见且有"重试"入口 |
| 载入示例模板 | templateId | 完整项目（ESP32 + DHT11 + OLED，连线齐备） | 模板缺失 → 提示 | 载入后运行结果为 `passed`（AC-09） |

### 15.3 发布与回滚

| 项 | 方案 |
| --- | --- |
| 发布方式 | 前端：构建产物发布到静态托管（版本化目录 + 原子切换）；后端：容器镜像（tag = commit SHA）滚动更新 |
| 发布前置 | `pnpm -r build` 通过、全部门禁绿、DB 迁移（如有）已审、回滚镜像已就绪 |
| DB 迁移 | Prisma migrate；每个迁移必须提供 `down` 方案说明（或明确"仅新增列/表，回滚=保留但不用"），执行前备份 |
| 回滚 | 前端：切回上一版本目录（< 1 min）；后端：回滚到上一镜像（< 5 min）；DB：按迁移说明回退或前向修复（不删数据） |
| 灰度 | 后端按 10% → 50% → 100% 放量；放量门禁 = 错误率 < 1% 且 `/validate` P95 < 500 ms |
| 变更窗口 | 避开教学高峰时段；规则集版本变更（会影响既有项目结论）必须公告（见风险 RK-08） |
| 数据兼容 | 规则集/定义升级不得静默改变老项目的诊断结论——老项目按其记录的 `ruleSetVersion` 复现，UI 提示"有新规则集可用" |

### 15.4 监控、告警与巡检

| 项 | 内容 |
| --- | --- |
| 核心指标 | 可用性（`/health` 成功率）、`/validate` 请求量/P95 耗时/错误率、项目保存失败率、导入失败率、前端 JS 错误率、首屏 LCP |
| 日志 | 结构化 JSON，含 `requestId`、`route`、`durationMs`、`ruleSetVersion`、`diagnosticCount`；不记敏感内容（本项目无敏感数据） |
| 告警 | ① 5 分钟错误率 > 1% 告警；② `/validate` P95 > 800 ms 持续 10 分钟告警；③ `/health` 连续 3 次失败告警；④ 项目保存失败率 > 5% 告警 |
| 渠道与责任 | 告警进团队群 + 值班人；负责人：后端 Owner（接口）、前端 Owner（画布与性能） |
| 巡检 | 日：错误日志抽查、`/validate` 慢请求 Top 10；周：规则命中率统计（哪些规则从未命中 → 疑似无效）、定义数据来源链接可访问性、备份可恢复性抽检 |
| 关键指标口径 | 「错误率」= 5xx 响应数 / 总请求数；「P95 耗时」= 仅统计 status=200 的 `/validate` 请求 |
